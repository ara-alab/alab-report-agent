# MVP 구현 계획

MES/ERP 데이터를 조회·분석해 기업 서식 보고서를 자동 기안하는 AI Agent의 MVP 범위와 구현 계획

## 1. 목표

| 항목 | 내용 |
| --- | --- |
| 과제 | MES/ERP 연계형 지능형 보고서 기안 AI Agent |
| 목표 수준 | 핵심기능 3~5개와 End-to-End Workflow 1개가 안정적으로 동작하는 MVP |
| 개발 기간 | 8일 |
| 핵심 가치 | 자연어 요청 → 데이터 자동 조회 → 분석 → 서식 기안 → 근거 검증을 하나의 흐름으로 수행 |
| 주제 적합성 | 제조·피지컬 AI — 설비 측정값의 규격 이탈 판정을 생산·품질 보고서와 연결 |

## 2. 설계 원칙

| 항목 | 원칙 |
| --- | --- |
| 편집 화면 | 목업 HTML 지면 유지, 직접 편집은 최소화하고 상세 수정은 Agent 대화로 처리 |
| 프런트 | `public/report-mockup/index.html` 유지, 신규 로직은 별도 JS 파일로 분리 |
| 서버 | 같은 Next.js 앱의 API route에 Agent·조회·저장·출력 기능 추가 |
| LLM | Anthropic 호출 계층·모델 구성 |
| 데이터 | MariaDB(MySQL 호환) 기반 가상 MES 스키마, 테이블·데이터 추가가 쉬운 구조 |
| 데이터 조회 | 사전 정의 조회 함수 우선, 부족하면 LLM이 읽기 전용 SQL 생성 |
| 수치 산출 | 수치는 코드로 계산, LLM은 판단 및 서술 작성·수정 담당 |
| 서식 | 목업 서식(`weekly-summary.html`)과 Agent 서식(`data/templates/agent/`) 등록형, LLM이 서식 수정·신규 작성 가능 |
| 문서 출력 | HTML 지면·브라우저 인쇄(PDF), HWPX/DOCX는 후속 고도화 |
| 실행 환경 | 로컬 개발, 시연은 로컬과 서버 배포 구성 모두 대응 |
| 범용성 | 특정 기업·업종 전용이 아닌 범용 MES/ERP 연계 보고서 Agent, 현장 지식은 데이터 계층에만 둠 |

### 범용성 원칙

- 공통 계층(`src/lib/agent/`·`src/lib/llm/`·SQL 가드·카탈로그 로직)에는 업종 용어·공정명·코드값·테이블명·기대 수치를 쓰지 않음
- 현장 지식 위치: 테이블·컬럼 의미와 업무 규칙은 카탈로그 설명(`src/lib/catalog/tables.ts`), KPI 공식·기본 집계 범위는 지표 정의(`src/lib/catalog/metrics.ts`), 측정 항목·규격 한계값은 DB 측정 항목·규격 테이블(`eq110`·`eq120`), 코드 의미는 DB 코드 테이블, 사용자 범위는 계정 설정(`src/lib/accounts/`)
- 조회 함수는 스키마 어댑터 — 파라미터 허용값은 코드에 고정하지 않고 DB 실측값으로 검증
- 결과 불일치 시 수정 순서: 데이터 설명 보강 → 범용 조회·분석 능력 보강 → 업종 무관 일반 규칙
- 특정 요청·시연 정답만 통과시키는 규칙·분기·프롬프트 문구는 추가하지 않음
- 시연 요청 세트는 측정 수단이며 맞춤 대상이 아님 — 시드 이상 사례와 무관한 일반 요청을 함께 측정
- 날짜 관행: 월 주차는 KS X ISO 8601(월요일 시작, 첫 목요일이 속한 주가 1주), 주차 기간은 코드(`src/lib/calendar.ts`)로 산출하고 응답에 실제 날짜 범위 병기
- 공정 간 합산: 흐름 수량(지시·양품)은 합산하지 않고 기준 공정 값 사용, 사건 수량(불량·정지·경보)은 합산하고 공정별 내역 병기, 기준 공정은 카탈로그 설명에 둠

## 3. 샘플 계정

| 계정 | 역할 | 주 사용 흐름 |
| --- | --- | --- |
| 생산기술부 김도현 과장 | 생산 보고 기안자 | 생산실적 보고서 요청·대화 수정 |
| 품질보증팀 서민재 대리 | 품질 보고 기안자 | 불량 로그와 설비 이상 판정 중심 품질 보고서 요청 |
| 이상훈 부장 | 검토·승인자 | 전체 저장 보고서의 수치가 실제 데이터 근거를 갖는지 근거 패널·정합성 검증으로 확인·검토 |

- 실제 로그인 없이 타이틀바 계정 칩에서 계정 전환
- 계정별로 기안자 정보·결재선·조회 가능 테이블 범위를 다르게 적용
- 보고 대상·서식은 요청 문장에서 추출, 없으면 계정 설정의 최종 결재자·기본 서식 사용 — 기본 서식은 현재 설정값만 보유, 화면 미적용
- 문서번호·발행일은 보고서 저장소가 발번·기록
- 조회 범위는 SQL 가드의 계정별 허용 테이블 목록으로 제한

## 4. 생성 흐름

| 흐름 | 구분 | 동작 |
| --- | --- | --- |
| 대화로 시작 | 메인 | 자연어 요청 → Agent가 데이터 판단·조회·분석 → 서식까지 자동 결정해 바로 기안 |
| 템플릿으로 시작 | 메인 | 자연어 요청 → Agent가 대화로 추천 서식 카드 제시 → 사용자 선택 → 조회·분석·기안 |
| 데이터로 시작 | 보류 | 목업 더미 창 삭제 — 좌측 레일 데이터 탭이 계정 조회 범위의 실제 테이블 목록·구조·표본 제공 |
| 보고서 통합 | 후속 고도화 | Agent가 생성·저장한 보고서 선택 → 저장된 구조화 데이터로 통합 보고서 기안, 시연 범위 제외 |

- 대화로 시작: 목업의 근거 원천 선택 카드 단계를 Agent 자동 판단으로 대체
- 템플릿으로 시작: `templates/index.json`의 고정 추천·적합도를 Agent 추천으로 대체
- 보고서 통합: 원천을 일일 보고서 JSON에서 저장된 Agent 보고서로 교체하는 후속 고도화, 현재 목업 통합 창은 일일 보고서 더미 원천 유지·시작 화면 미노출

## 5. 시연 시나리오

| 단계 | 사용자 | Agent·시스템 |
| --- | --- | --- |
| ① 요청 | 대화 입력란에 자연어로 보고서 요청 | 기간·대상·보고서 유형·필요 KPI를 구조화 출력으로 추출 |
| ② 조회 | 조회 계획과 진행 상황 확인 | 조회 함수 tool 호출, 부족하면 SQL 생성 후 실행 |
| ③ 분석 | KPI 요약과 이상 항목 확인 | 달성률·증감률·불량률(PPM)·가동률 계산, 설비 측정값을 규격 테이블과 대조한 이상 판정, 이탈 일자와 비이탈 일자의 실적·KPI 대조로 영향 분석, 원인 서술 작성 |
| ④ 기안 | 서식 자동 결정 또는 추천 서식 선택 후 초안 확인 | 서식 키와 분석 결과 매핑, 수치는 계산값 그대로, 서술 칸만 LLM이 작성 |
| ⑤ 수정 | "불량 원인 부분 더 자세히" 같은 대화 지시 | 섹션 단위 재작성 |
| ⑥ 검증 | 수치 선택 시 근거 쿼리·원본 행과 정합성 배지 확인 | 수치별 출처 기록, 보고서 수치와 원본 대조 |
| ⑦ 저장 | 보고서 저장 | 본문·KPI 값·분자/분모·수치별 출처를 구조화해 저장 |
| ⑧ 검토 | 검토·승인자가 저장 보고서를 열어 수치 근거·정합성 확인 | 저장된 출처로 원본 재조회, 수치별 판정과 근거 쿼리·원본 행 표시 |
| ⑨ 출력 | 인쇄·PDF 저장 | 브라우저 인쇄 |

### 화면

| 구성 요소 | 위치(예정) | 내용 |
| --- | --- | --- |
| 화면 연동 | `public/report-mockup/js/` | Agent 호출·스트림 표시, 지면 갱신, 근거 패널, 계정 전환, 보고서 목록 |

- 저장 보고서 지면: `GET /api/reports/{id}?account={계정}` 응답의 `html`(저장된 채움 값으로 서식 재렌더, 조회·LLM 미호출) — 목록은 `GET /api/reports?account={계정}`
- 보고서 목록: 좌측 레일 보고서 탭 — 선택 계정의 목록 표시(적재는 `public/report-mockup/js/reports.js`), 「열기」는 아래 진입점 경로로 지면 표시, 탭 진입·계정 전환·저장 직후 갱신
- 저장 보고서 진입점: 목업 주소에 `?report={id}[&account={계정}]` 지정 시 해당 보고서를 지면에 표시 — 보고서 탭 「열기」와 주소 직접 진입 공용
- 임시 목록 페이지: `/report-mockup/reports.html?account={계정}` — ID·문서번호·제목·작성자·기간·작성/수정 시각 표, 제목 선택 시 위 진입점으로 열기
- 테스트 케이스 리포트: `/report-mockup/eval.html` — 타이틀바 링크로 이동, `public/eval-data/results.json`(성과지표·테스트 케이스 측정 결과)과 `public/eval-data/runs/index.ndjson`(실행 기록 목록)을 정적 파일로 읽음, 위에서부터 성과지표 요약·테스트 케이스·검증 루프 집계·실행 기록, 실행 ID·실행 행 선택 시 이벤트 타임라인
- 실행 기록: `ALAB_AGENT_RUN_RECORD=1` 일 때만 `POST /api/agent` 1회마다 `runs/{runId}.ndjson`(요청 정보 + 스트림 이벤트, 연속 본문 조각 병합·경과 ms)과 목록 요약 1줄 저장, `runId` 는 `start` 이벤트로 전달 — 저장 실패는 응답에 영향 없음
- 수치 근거: `GET /api/reports/{id}/evidence?account={계정}&key={수치 키}` — 수치 1건의 판정·저장/원본 값·조회 조건·SQL·산식·원본 행·원천 테이블, 좌측 레일 근거 탭이 사용
- 정합성 검증: `GET /api/reports/{id}/verify?account={계정}` — 저장 수치 전체의 판정(일치·불일치·원천 없음·출처 없음)별 건수·일치율과 수치별 판정, 서로 다른 출처 조회 60건 상한, 리본 정합성 검증 버튼이 사용
- 조회 범위: 근거·검증 모두 단건 조회와 같은 계정 범위, 재조회는 작성 계정 권한 — 없는 보고서 404(`not_found`), 검증 불가 `not_verifiable`
- 데이터 탭: `GET /api/datasets?account={계정}`(테이블 목록·적재 기간) · `GET /api/datasets/{table}?account={계정}`(구조·표본, 범위 밖 400)
- 서식 틀: `GET /api/templates/{id}/preview?account={계정}` — 계정·시스템 키만 채운 지면, 초안 도착 전 표시, 없는 서식 404
- Agent 초안 지면은 임시로 A4 비율을 해제하고 내용 높이만큼 세로 확장 — 연속 스크롤 지면·드로어 패널 변경은 별도 작업

## 7. Agent tool

| tool | 역할 |
| --- | --- |
| `list_datasets` / `describe_table` | 사용 가능한 테이블과 컬럼 의미 조회 |
| `resolve_week` | 월 주차별 실제 기간 산출 |
| `query_*` | 사전 정의 집계 조회, 결과에 출처 ID 부여, 명칭 마스터가 있는 코드는 명칭 함께 반환 |
| `run_sql` | 조회 함수로 부족할 때 SQL 생성·실행, 가드 통과분만 실행 |
| `analyze_kpi` | KPI 비율·직전 기간 증감·개선/악화 계산, 결과는 코드 산출값, 집계 단위·범위 값에 명칭(`groupName`·`valueName`) 병기 |
| `check_limits` | 측정값의 규격 이탈 항목·시각·이탈 일자별 건수 판정, 규격으로 설명되지 않는 경보 건수 대조, 대상·대상 구분 명칭(`entityName`·`entityTypeName`) 병기 |
| `recommend_templates` | 요청에 맞는 서식 후보와 추천 사유 제시 |
| `propose_templates` | 서식 후보 1~3개와 사유를 화면 카드(`templates` 이벤트)로 제시하고 응답 종료, 용도가 맞는 서식이 여럿이거나 사용자가 서식 선택을 원할 때 모델 판단으로 호출(규칙 14) |
| `draft_report` | 서식 키 매핑과 서술 작성, 지면 생성 |
| 섹션 수정 | 별도 tool 없이 요청 `section` 필드로 지정한 키만 `draft_report` `revise: true` 로 교체, 다른 키 변경·전체 재작성·서식 제안은 서버 거부 |
| `edit_template` | 서식 수정·신규 작성, 후속 고도화 |
| `save_report` / `list_reports` | 보고서 저장, 저장 보고서 목록 조회 |
| `merge_reports` | 저장 보고서의 구조화 데이터로 통합 보고서 기안, 후속 고도화 |

- 코드값 표기: 서술은 명칭만, 명칭만으로 구분이 어려우면 첫 언급에만 명칭(코드), 표는 명칭 열과 코드 열 분리, 명칭 마스터가 없는 코드는 그대로(규칙 13) — 명칭 원천은 `src/lib/catalog/metrics.ts` 선언
- 이상 구간 영향 분석은 별도 tool 없이 Agent 단계로 수행 — `check_limits`의 이탈 일자로 구간을 정하고 `analyze_kpi`·`query_*`로 이탈 일자와 비이탈 일자의 일 단위 실적을 대조

## 9. 성과지표와 테스트 케이스

- 성과지표와 테스트 케이스는 분리 — 성과지표는 시연 요청 세트의 품질 수치, 테스트 케이스는 입력·예상결과·실제결과 묶음의 통과 여부
- 측정 정의: 성과지표는 `scripts/eval/metrics.json`, 테스트 케이스는 `scripts/eval/cases.json` — 저장소 추적
- 측정 실행: `node scripts/eval/run.mjs [--cases] [--metrics] [--only TC1,R2] [--note "수정 내용"]` — 서버를 `ALAB_AGENT_RUN_RECORD=1` 로 실행한 로컬 개발 서버 대상(`EVAL_BASE_URL`, 기본 `http://localhost:3002`), 인자 없으면 둘 다 실행
- 측정 결과: `public/eval-data/results.json`(저장소 추적, 데모 빌드에 포함) — 테스트 케이스 리포트(`/report-mockup/eval.html`)로 제시
- 측정 직전 보고서 저장소(`alab_report` 스키마)의 시험 저장분 비움 — 비울 테이블 범위는 실행 전 확인

### 성과지표

| 평가항목 | 목표 | 측정 방법 |
| --- | --- | --- |
| 데이터 조회 성공률 | 95% | 시연 요청 세트 실행 시 조회 도구 호출 중 오류·빈 결과가 아닌 비율 |
| 필수항목 자동작성률 | 90% | 기대 서식의 필수 키 중 조회·서술 키(시스템·계정 발급 키 제외)가 채워진 비율 |
| 원본 데이터-보고서 수치 일치율 | 95% | 요청 세트 초안을 시험 저장분(제목 「 [검증용]」)으로 저장 후 근거 검증 모듈 대조, 출처 없는 수치는 불일치로 계산 |
| Template Mapping 정확도 | 90% | 정답표 대비 서식 선택·기간 키 값·조회 키별 기대 원천(도구 묶음, 요청 기간 또는 직전 비교 기간 안의 조회) 일치 비율 |
| 이상 판정 정확도 | 시드 이상 사례 검출 100%, 오탐 0건 | 전체 시드 기간 `check_limits` 결과와 시드 이상 사례(설비·측정 항목·이탈 일자) 정답표 대조, 사례 밖 이탈 일자·규격으로 설명되지 않는 경보 건수 — LLM 미사용 |

- 시연 요청 세트는 시드 이상 사례 기반 요청과 이와 무관한 일반 요청을 함께 포함
- 통합 보고서 수치 일치율은 후속 고도화 — 보고서 통합 기능(§4) 구현 후 측정 대상에 포함
- 도입 전후 비교 수치(처리시간 등)는 측정하지 않음 — 사람 작성 시간 실측이 없어 개선효과 수치로 제시하지 않음

### 테스트 케이스

| 범주 | 건수 | 판정 기준 |
| --- | --- | --- |
| 정상 입력 | 2 | 기대 서식·기간의 초안이 검증 통과해 작성됨 |
| 부정확한 입력 | 1 | 대상·기간을 추측해 초안을 만들지 않고 확인 질문을 함 |
| 악의적 입력 | 1 | 권한 밖 데이터 미조회·권한 없음 안내, 원본과 다른 수치가 담긴 보고서 미저장 |
| 데이터 없음 | 1 | 빈 데이터로 초안을 만들지 않고 적재 기간 안내 |

- 판정: 케이스별 판정 항목(초안·저장 여부, 서식, 기간, 오류 코드, 답변·초안 포함 문구, 성공 도구 호출 입력, 저장 수치 재조회 일치)을 실행 이벤트로 자동 대조
- 수정 내역: 케이스별 실행 이력(시각·실행 ID·판정·측정 시점 커밋·미커밋 변경 여부·`--note` 수정 내용)을 결과 파일에 누적 — 실패 후 코드·프롬프트·데이터 설명을 고쳐 다시 실행한 기록
- 도구 오류·AI 제공사 API 오류는 입력으로 재현할 수 없어 고정 케이스로 두지 않음 — 실제 실행에서 발생한 오류는 검증 루프 집계와 실행 기록으로 제시

## 10. 대화 맥락 유지

- 방식: 화면이 턴별 재사용 조회(이름·입력)를 assistant 이력의 `queries` 로 보관해 전송, 서버가 LLM 호출 전 재실행해 조회 결과 캐시 복원과 이전 턴 tool 호출·결과 블록 재구성
- 근거: 조회 ID는 tool 이름·입력의 해시(`src/lib/queries/registry.ts` `queryIdOf`)라 재실행 시 같은 ID, 이전 턴 참조 그대로 유효
- 재실행은 DB 조회만 수행, LLM 미호출 — 결과는 재실행 시점 DB 값

| 단계 | 위치 | 내용 |
| --- | --- | --- |
| 1 | 화면 | `done.queries` 를 해당 assistant 발화의 `queries` 로 보관, 다음 요청에 함께 전송 — 목업에 개발용 연동, 실구현은 화면 연동 담당 |
| 2 | `src/lib/agent/request.ts` | `queries` 검증 — assistant 발화만, 계정 허용 조회 tool·분석 tool·`run_sql` 만, 턴당 30건·전체 60건·입력 JSON 2,000자 상한 |
| 3 | `src/lib/agent/run.ts` | 루프 전 이전 턴 조회 재실행, 사용자 발화 → assistant tool 호출 → tool 결과 → assistant 답변 순으로 재구성, 재실행 오류 조회는 제외하고 `agent_history_drop` 로그 기록 |
| 4 | `src/lib/agent/prompt.ts` 규칙 15 | 이전 턴 조회는 같은 조회 ID로 참조, 같은 조건은 다시 조회하지 않고 부족한 조회만 추가 |
| 5 | `run.ts` `agent_step` 로그 | 단계별 tool 이름 기록 — 재조회 여부를 로그로 판정 |
| 6 | 화면·`run.ts` | 최근 초안 1건의 검증된 입력을 assistant 이력의 `draft` 로 보관·전송, 서버가 복원 조회 결과로 LLM 없이 재검증해 `draft_report` 호출·결과 블록 재구성, 저장·수정 요청 시 재작성 없이 `save_report`·`revise` 처리(규칙 18), 재검증 실패 초안은 제외하고 `agent_history_drop` 로그 기록 |

- 입력 토큰: 이전 조회 결과만큼 증가, 프롬프트 캐시(시스템·대화 끝 중단점)로 재사용분 상쇄
- 합성 tool 호출 블록은 사고 블록 없이 전달 — 기본 설정에서 API 수용 확인
- 검증 기준: 2턴째 같은 조건 재조회 0건, 이전 턴 조회 ID를 참조한 초안 통과 — 서식 키에 필요한 조회가 1턴에 없으면 2턴 추가 조회는 정상

## 11. 초안 명시 저장 (3일차 화면 연동 단계 적용)

- 방식: 화면이 보관한 초안을 저장 버튼으로 기존 `POST /api/reports` 에 전송 — LLM 저장 요청 없이 사용자가 명시 저장, 서버 변경 없음
- 초안 원천: `draft` 이벤트(`src/lib/agent/run.ts`)의 서식·제목·기간·채움 값·수치 — 화면 `lastDraft` 보관(`public/report-mockup/index.html` `showDraft`)

| 단계 | 위치 | 변경 |
| --- | --- | --- |
| 1 | 화면 `sendAgentChat` | `saved` 이벤트의 `id`·`docNo` 를 현재 초안의 저장 상태로 보관, 새 `draft` 이벤트 수신 시 미저장 상태로 전환 |
| 2 | 화면 저장 버튼 | `lastDraft` 를 `{templateId, title, periodFrom, periodTo, requestText, fills, numbers, draft}` 로 변환해 `POST /api/reports`, 저장 상태에 `id` 가 있으면 함께 전송해 같은 문서번호로 갱신 |
| 3 | 화면 저장 결과 | 응답의 `id`·`docNo` 를 저장 상태에 반영, 문서번호 표시, 저장 보고서 열기(`?report=`)와 같은 상태로 전환 |

- 갱신은 작성 계정 본인만 가능, 서식 변경 불가 — 다른 계정·서식이면 서버 오류 문구 표시(`src/lib/reports/index.ts` `saveReport`)
- 제약: `lastDraft` 는 페이지 메모리 보관이라 새로고침 시 저장 전 초안 소실
- 기안 기록: `draft`(기안 입력·조회 원천)는 `report.draft` 컬럼에 보관 — 저장본 수정 시 조회 재실행·재검증 원천
- 제약: 저장 시 서버는 채움 값 구조만 검사하고 수치와 조회 결과의 일치는 대조하지 않음 — 정합성 검증(`GET /api/reports/{id}/verify`)으로 확인
- 목업 연동: 리본 저장 단추(`saveBtn`) — 지면에 Agent 초안이 있을 때만 활성, 저장 응답 전까지 잠금으로 중복 발번 방지, 타이틀바 저장 상태(저장 안 됨·저장 중·저장됨과 문서번호) 표시, 저장 후 `GET /api/reports/{id}` 로 지면 재표시, 연 저장본은 문서번호를 표시하고 수정 초안 저장 시 같은 보고서 갱신
- 검증: 재생 스트림 초안 표시 후 버튼 저장 → 목록 반영·문서번호 발급, 같은 초안 재저장 시 문서번호 유지, LLM 저장 직후 버튼 저장 시 신규 발번 없음

## 12. Agent 요청·이벤트 계약

- 진입점: `POST /api/agent` — 응답은 NDJSON 이벤트 스트림, 요청 검증 실패는 400(`code`: `bad_request`·`bad_account`·`bad_report`)
- 모든 필드는 선택 — 생략 시 기존 동작(모델이 규칙 14로 초안 작성 여부 판단)

| 요청 필드 | 형식 | 내용 |
| --- | --- | --- |
| `messages` | `[{role, content, queries?, draft?}]` | 대화 이력, 마지막은 사용자 발화, 최대 20건·발화당 4,000자 |
| `messages[].queries` | `[{name, input}]` | assistant 발화에만, 직전 응답 `done.queries` 를 그대로 보관 |
| `messages[].draft` | `{input, saved?: {id, docNo}}` | assistant 발화에만, `draft` 이벤트의 `input` 과 저장 상태 보관, 입력 JSON 40,000자 상한, 서버는 마지막 1건만 복원 |
| `account` | 문자열 | 샘플 계정 ID |
| `mode` | `"draft"` \| `"ask"` | 작성 모드는 초안 작성, 질문 모드는 대화 답변 — 화면은 대화창 스위치 |
| `template` | 서식 ID | 작성 모드 전용, 해당 서식으로 고정, 없는 ID는 400 |
| `report` | 보고서 ID | 저장 보고서 수정, 기안 기록을 조회 재실행으로 재검증해 초안으로 복원·같은 문서번호로 갱신, 없는 보고서·작성자 아님·기안 기록 없음은 400 `bad_report`, 재검증 실패는 `report_not_editable` 오류 이벤트 |
| `section` | 서식 키 | 해당 섹션만 수정, 작성 모드로 고정·`"ask"` 와 함께 쓸 수 없음, 초안 없으면 `no_draft`, 시스템·계정·조회 메타 키는 `bad_section` |

| 이벤트 | 필드 | 내용 |
| --- | --- | --- |
| `start` | `model`, `account`, `runId?` | 응답 시작, `runId` 는 실행 기록 저장 시에만 |
| `plan` | `step`, `calls[{id, name, input}]` | 단계의 기안 외 tool 호출 목록, 실행 전 일괄 통지 |
| `tool_call` / `tool_result` | `id`, `name`, `input` / `ok`, `error`, `errorKind`, `issues[{at, kind}]`, `queryId`, `rowCount` | tool 1건 실행 전후, 오류 범주는 실패 시에만 |
| `delta` | `text` | 답변 본문 조각 |
| `retry` | `reason` | `max_tokens`(출력 한도 잘림 재작성)·`draft_missing`(작성 모드 초안 재지시), 그 전 본문은 중간 안내로 분리 |
| `draft` / `saved` | 초안(서식·제목·기간·채움 값·수치·`html`·`input`) / `id`, `docNo` | 초안 생성 / 저장 완료, `input` 은 검증된 기안 입력으로 다음 요청 `messages[].draft` 원천 |
| `templates` | `candidates[{id, name, reason}]` | 서식 후보 카드 — 선택 시 `mode: "draft"`, `template` 으로 다음 요청 |
| `error` | `error`, `code` | 오류 — 작성 모드에서 초안 없이 끝나면 `draft_failed`, 빈 답변은 `empty_answer` |
| `done` | `model`, `steps`, `sources`, `queries`, `usage` | 종료, `queries` 는 이번 턴 재사용 조회 |

- 오류 범주(`errorKind`·`issues[].kind`): 초안 검증 `bare_number`(참조 없는 숫자)·`char_limit`(글자 수 초과)·`ref`(참조 오류)·`unknown_key`(서식에 없는 키)·`format`(입력 형식)·`template`(서식) · 기안 tool `rule`(모드·섹션·revise 순서 위반)·`report`(저장) · 조회 `param`(조회 조건)·`sql_guard`(SQL 가드 거부)·`sql_error`(SQL 실행)·`catalog`(데이터 설명)·`unknown_tool` — 초안 검증 실패는 `issues` 에 키별 범주, `errorKind` 는 첫 범주, 모델에 돌려주는 오류 문구는 범주와 무관하게 동일
- 서버 강제: 질문 모드는 기안·저장·서식 제안 tool 거부, 작성 모드는 초안 없이 끝나면 1회 재지시, 서식 고정 시 다른 서식 초안·서식 제안 거부, 섹션 수정 시 지정 키 외 변경·전체 재작성·서식 제안 거부
- 작성 모드·서식 지시는 마지막 사용자 발화 끝에만 덧붙임 — tool 정의·시스템 프롬프트는 모드와 무관하게 공통이라 프롬프트 캐시 유지
- 서식 제안: 요청 필드 없이 모델이 규칙 14로 판단 — 제안 성공 시 서버가 `templates` 이벤트 후 응답 종료
- 초안 미리보기 작성일: 초안 작성 일자(KST), 문서번호·결재일은 저장 시 기록
- 수치 검증 범위: 참조 검증은 `draft_report` 초안 수치만 대상, 대화 답변 본문의 수치는 검증하지 않음 — 프롬프트 규칙(도구 조회 결과에서만 인용)으로만 제한
- 목업 연동(`public/report-mockup/index.html`): 대화창 작성 모드 스위치(자동·작성·질문), `plan` 단계·도구 묶음 표시, `templates` 카드 선택(서식명·사유 표시), 리본 저장 단추와 저장 상태 — `queries`·`draft` 이력 보관, 섹션 선택 수정 입력, 검증 과정 기본 표시(도구 오류 범주, 초안 검증 실패 범주·위치와 재작성 차수, `retry` 재지시, 종료 요약)는 개발용 연동 유지(동작·스타일은 화면 실구현 단계에서 교체)
